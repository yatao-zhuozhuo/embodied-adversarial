# Baseline、SFT、GRPO 多轮输入统一方案

日期：2026-10-06。状态：**目标规范，待实施与验收**。

本文承接 [XML 输出协议统一方案](trajectory-xml-protocol-unification.zh-CN.md)，规定三个链路如何构造模型的下一轮输入。输出继续使用 `openeta.two_tool_xml.v1`，模型工具仍只有 `observe_env`、`step_env`。

本文不修改当前采集、评测、训练或 checkpoint；不要求停止现有实验，也不要求额外进行短 SFT。各链路的 XML 实现已经有所推进，但**输入契约尚未按本文统一**。

## 1. 总体结论

统一的是**字段语义、构造流程、历史选择和可见信息边界**，不是让所有 benchmark 使用相同图片数量、动作维度或相同任务文字。

目标采用：

1. 一个共享上下文构造器，供 baseline、SFT 采集/导出、GRPO rollout/训练/评测共同调用。
2. 每个 benchmark 的版本化相机与控制器 profile；必要的任务/机器人差异通过显式子 profile 表达。
3. 最新观测＋明确执行反馈＋最近四个完整决策组的文本历史。
4. 按 benchmark 提供当前有效视角，并增加上一决策前的主视角用于比较；不把所有历史图片反复传入。
5. 模型输出原文和完整轨迹继续保留；发送给下一轮的历史只保留回答中的 XML，不重复发送历史隐藏思考文本。
6. 每轮保存实际模型输入及其图片顺序，Swift 必须在同一个条件上下文下计算训练概率。

**同一 benchmark、同一子 profile、同一观测和动作历史，三个链路必须产生等价输入。** 模型专用聊天模板、图像 token 编码可以不同，但不能悄悄改变可见状态、相机选择、历史长度或动作含义。Alice/Bob 的任务目标和角色指令可以不同，观测契约与反馈字段保持一致。

## 2. 复核依据与证据边界

### 2.1 当前三条链路

| 链路 | 当前主要差异 | 入口 |
|---|---|---|
| Baseline | 当前主图＋可选手腕图；主图要求 512；历史最多 24 条消息/16000 字符；正常动作后的 feedback 常为空 | `.worktrees/baseline/baseline/runtime/run.py` |
| SFT | 默认取相机列表前两张；五轮历史带多模态消息；反馈不单列实际执行步数 | `scripts/collect_two_tool_sft.py` |
| GRPO | 每步一张策略视角图；历史随多轮累积；反馈已有实际执行步数；当前正式任务范围是 PickCube | `plugins/embodied_swift_grpo.py`、`agent/runtime/embodied_two_tool.py` |

最终实现不得继续保留三份相机选择、状态裁剪和提示词构造逻辑。

### 2.2 DeepSeek 实际检查范围

检查的是 [deepseek_xml_debug5_20261006_022309](../SFT_data/deepseek_xml_debug5_20261006_022309) 中四个 benchmark、每个 15 次尝试，共 60 条、2740 轮轨迹。它由 SFT 采集链路产生，**不是已确认的正式 baseline campaign**；baseline worktree 的结果目录中未找到对应 DeepSeek 结果。

该批轨迹成功数为 0，17 条因模型输出长度限制结束，38 条达到轮数上限；这些统计不能证明输入格式是全部失败原因。任务难度、控制器正确性、模型能力与预算还需分别验证。

与输入有关的直接证据：

- MetaWorld 的 15 条轨迹初始 `view` 和 `render` 文件内容相同，当前发送了重复图片。
- RoboCasa 的 15 条轨迹均保存 `agentview_left`、`agentview_right`、`wrist`，默认前两张策略让手腕图未进入模型输入。
- ManiSkill 的 15 条轨迹中，只有 3 条保存 `hand_camera`，其余 12 条没有。不能假设每个 ManiSkill 任务都有手腕相机；部分手腕图原生为 128×128。
- 模型原始回复反复推测动作坐标系、控制是否为关节控制、夹爪是否闭合以及动作是否生效。创建回执中虽有部分控制信息，模型输入未完整、统一表达这些信息。
- 某些任务文字仅为 `ManiSkill task: PickSingleYCB-v1` 或 `FMBAssembly1Easy-v1`，没有清楚的自然语言目标。
- 图片 content 块缺少相机、轮次、时间点的明确文字标签；模型需要自行判断哪个视角和哪个时刻。
- 22 条轨迹在宿主已经提供初始观测后，第一步仍调用观察。它可能反映重复观察需求或误解，不能单凭此统计认定全部都是无效动作。

因此，优先修正信息缺失和选择错误；不能通过“模型说看不清”直接认定图片没有送达，也不能把它对碰撞、关节极限的猜测写成环境事实。

### 2.3 与原 OpenETA 的关系

原主 planner 使用当前观测、工具回执、最近状态转移、对话与持久化记忆的有限投影；默认最近四个对话动作组、三次状态转移，并按上下文预算裁剪。视觉历史启用时选择初始主图、最近三次主图、当前手腕图，并可加入独立视觉差分摘要；实际附件数量还受入口配置和后端上限影响。

相关实现：[planner.py](../agent/runtime/planner.py)、[visual_history.py](../agent/runtime/visual_history.py)、[runtime_assembly.py](../agent/runtime/runtime_assembly.py)。这里是当前主 planner 与本地缓存 `origin/main` 的设计，不声称已追溯项目最早历史提交。

本文继承“当前证据清晰、历史有界、完整证据持久化”的原则。两工具版本暂不引入视觉差分模型、模型生成摘要、额外感知工具或通用 planner 的全部记忆能力。

## 3. 版本和共享构造流程

建议新增 `openeta.two_tool_input.v1`，并与现有 XML 输出协议独立记录。该名称为目标设计，尚未表示代码中已有实现。

建议共享模块职责如下；具体文件命名可在实施时确定：

```text
真实 MCP observation + 执行回执 + 宿主任务/控制契约 + 决策历史
    → 模型可见字段白名单
    → benchmark / task / robot profile
    → 相机选择、图像校验、时刻标注、去重
    → 动作前后本体状态差分
    → 四组历史与预算投影
    → 规范输入包（文本 + 有序图像 + 证据索引）
    → 模型/provider/Swift 模板适配器
```

profile 必须记录 ID、版本/hash、来源环境版本和控制模式。运行启动时校验环境能力；同一 profile 不能在不同链路偷偷选择不同相机。

模型专用适配器只负责 API 多模态消息、Swift `<image>` 与 `images` 的正确编码，不另行选择历史、改写任务或重新解释动作。

## 4. Benchmark 相机配置：数量可不同，规则必须一致

以下是**第一版待验收的默认配置**。图片上限指一次决策请求中的所有图片附件，不是仅最新一条 user 消息的数量。环境缺少视角、首轮无历史或图像重复时，实际数量可以更少。

| Benchmark | 当前观测的视角 | 历史图 | 请求上限 | 选择与回退 |
|---|---|---|---:|---|
| MetaWorld | 一个有效主视角，优先配置为 `render` | 上一决策前的同一主视角 | 2 | `render` 不可用时，仅允许已验证的 `view` 别名；两者相同则只送一次 |
| LIBERO | `agentview`＋当前 `wrist` | 上一决策前的 `agentview` | 3 | `render` 只有通过 profile 验证为所需主视角替代时才可回退，不额外凑第三张当前图 |
| ManiSkill | `base_camera`＋任务确实提供的 `hand_camera` | 上一决策前的 `base_camera` | 有手腕时 3；无手腕时 2 | 按任务/机器人子 profile 固定有无手腕；其他 render 视角是否更合适需单独验收，不能按返回顺序临时替换 |
| RoboCasa | `agentview_left`＋`agentview_right`＋当前 `wrist` | 上一决策前的左右主视角 | 5 | 保留左右空间信息及抓取视角；缺失时使用预声明的降级 profile，不能静默丢掉手腕图 |

### 4.1 分辨率与质量

- 第一版主视角目标为原生渲染 256×256；这是起始实验配置，不是已证明最优的分辨率。
- 手腕默认 256×256；仅支持 128×128 的相机允许在子 profile 中声明原生 128，不放大后声称信息增加。
- 相机位姿、裁剪、宽高比和缩放策略也必须固定。跨链路统一图像尺寸但改变拍摄视角，仍不算相同输入。
- 小物体、插装或目标区域看不清的任务，验证后可建立 384/512 分辨率子 profile。升级必须同时用于同任务的采集、训练和评测，并单独标记结果。
- 主视角缺失或损坏应作为观测错误处理。低方差是检查信号，不单凭统一方差阈值把正常静态图误判为故障。
- 不要求当前 PickCube GRPO 马上扩展四个 benchmark；它先使用相应 ManiSkill 子 profile。后续扩展时接入同一规则。

### 4.2 标签、时间与去重

每张图片前提供可读标签，并保存结构化索引：`image_id`、`camera_id`、`camera_role`、`observation_id`、`turn`、`timing`、`width/height`、对应动作 ID。

例如：`当前观测，turn=8，camera=wrist，动作7执行后`。历史图片明确写“历史”，不能把旧图当最新状态。

每次请求使用确定顺序：历史主视角（若有）→当前主视角→当前手腕视角。对相同解码像素或等价证据去重；同一图同时代表多个时间点时，在证据索引保留其全部时刻引用，并注明“相同图像”，不能默默丢掉时间关系。

上一决策无效或仅观察时，也按照真实 observation ID 和前后关系处理；不把“上一决策前”误写成“上一次移动前”。第一轮不补造历史图。默认不常驻初始参考图；只有经版本化配置与对照实验确认有效时才增加。

## 5. 统一模型可见信息

### 5.1 静态任务与动作契约

每次构造上下文都保留：任务自然语言、角色、两个工具及 XML 输出规则、控制器契约。不能只给 env ID；任务文字须来自环境/官方任务定义或经审计的等价描述，不补写专家动作流程。

动作契约至少包含：

- 控制器名称、实际 control mode、动作维度、每维上下界。
- 每个槽的语义、归一化方式、已验证的尺度/单位、参考坐标系。
- 旋转表示及坐标系；不能把未经确认的轴角增量标成 Euler 角。
- 夹爪正负方向和命令语义；移动底盘、torso、mode 的含义及模式约束。
- `num_steps` 的重复控制步语义、1–10 范围，以及实际执行步数可能少于请求的情况。
- TCP 位姿的坐标系、位置单位、四元数顺序；无法验证的字段标记 unknown，不用经验猜测填充。

当前常见动作维度：MetaWorld 4、LIBERO 7、ManiSkill 7、RoboCasa 12，仅作配置核查参考，最终以实际环境契约为准。必须核对 MetaWorld 夹爪方向、LIBERO/ManiSkill 控制坐标系、RoboCasa 底盘/手臂模式；字段不足时先修补环境契约来源，不能向模型输出错误说明。

不得直接把含 `move_to` 等其他工具建议的整段 `action_hint` 复制到两工具 prompt；只提取经确认的当前动作契约信息。

### 5.2 每轮动态输入

统一字段如下，名称为建议的目标 schema：

| 字段 | 含义 |
|---|---|
| `turn` / `observation_id` | 当前决策编号和当前观测引用，编号规则固定 |
| `budget` | 剩余决策轮数、剩余环境控制步数 |
| `last_action` | 上一决策 ID、工具名、实际校验后的参数、请求步数、实际执行步数 |
| `execution` | `initial` / `executed` / `rejected` / `error`，结构化错误及执行结果是否确定 |
| `robot` | 当前关节状态、TCP 位姿、夹爪状态、必要时底盘状态 |
| `robot_delta` | 与上一决策前观测相比的已测本体状态变化 |
| `observation` | 当前是否新观测、相机可用性、图片证据索引与必要的标定信息 |
| `terminated` / `truncated` | 环境终止信息；episode 已终止通常不再发下一轮 |

`robot_delta` 推荐提供同一坐标系下的 TCP 位移及其长度、夹爪测量变化；姿态差只有在四元数顺序与单位验证后计算。底盘移动时需明确差分参考系。缺失或不同坐标系导致不可计算时填 null 并说明原因。

实际位移来自前后观测，不能由动作向量乘理想尺度冒充。模型可据此发现“小动作/无明显运动”，但宿主不能无证据宣布碰撞、抓取成功或关节极限。

`execution=executed` 仅表示工具执行正常，不表示任务成功。传输中断且动作可能已发送时，执行结果与步数可以 unknown；禁止将其标成 rejected/0 并盲目重试。

### 5.3 可见性边界

不向模型发送：环境 reward、训练 reward、隐藏成功评分、对象/目标真值坐标、仿真内部状态、快照路径、会话 handle。相机/机器人校准是可用的设备信息，不与隐藏对象真值混淆；跨链路提供相同且经过验证的表示。

Bob 可以看到按任务协议生成的可视目标标记，Alice/Bob 的宿主任务检查可以不同；必须显式记录差异，不能把 Alice 的轨迹或不可见目标状态提供给 Bob。

`gripper command` 与 `measured gripper state` 分开；缺测填 null。`observe_env` 明确描述为只观察，不会移动相机、提高分辨率或提供不同视角，避免把再次观察误解成“自动看得更清楚”。

## 6. 历史和消息布局

### 6.1 统一历史选择

保留最近四个完整决策组。每组记录：上一轮模型的最终 XML/无效回答文本、对应的精简执行回执。无效决策也计入，防止错误循环的证据被删除。

原始长 thinking、完整 provider 响应和环境回执持久化保存，但默认不重复作为下一轮历史输入。XML 内的 `<reasoning>` 是回答的一部分，保持原文。当前轮生成思考是否参与训练由训练策略决定，不能因不重放历史思考而错误删除当前轮生成 token。

历史图不随每组消息累积；统一由相机 profile 从观测账本选择。任务与动作契约不会随着滑窗丢失。

### 6.2 消息表达

统一为 system 任务/协议契约＋有界文本对话＋当前多模态 user 输入；XML 模式不同时启用原生 function-call 模板。

```text
system：任务、角色、控制契约、XML 规则、输入标签说明
user/assistant：至多四组历史文本，保留动作与对应执行反馈
user（最新）：当前预算、robot、robot_delta、上一执行回执、图片标签与有序附件
assistant（待生成）：可有模型支持的 thinking；最终回答为 XML decision
```

历史中的 user 文字和最新输入如何拆分必须由共享渲染器固定，不在三个链路自行拼接。最新执行回执若已放入最终 user 包，就不在历史里再重复一份。历史图片的文字引用不得误导为该旧消息仍含附件；真正附件只按本次图片索引发送。

### 6.3 上下文预算

四组历史是上限。以实际模板/tokenizer/视觉编码计数并预留生成预算；固定顺序裁剪最老的完整文本组，再按 profile 的优先级裁剪历史图。任务、动作契约、当前执行反馈、当前必要图像必须保留；最小输入仍超限时明确报错，不静默换视角或降低图片质量。

不同模型 token 化可以不同。主对比实验应预先选择各模型均能容纳的统一 profile 和预算，避免某个模型长期得到更少历史；发生裁剪时记录原因、保留组数/图片清单。生成长度不足与输入超限分开统计，不能把长 thinking 截断归因于图片太多。

## 7. 三条链路分别怎么改

### 7.1 Baseline

- 用共享输入构造器替换 `project_observation` 的独立相机选择及 `history[-24:]`/16000 字符裁剪。
- 每轮构造真实执行回执；正常执行也反馈工具、参数、请求/实际控制步数和本体状态差分，feedback 不再只在报错时有内容。
- 历史保留真实动作与结果，替换仅有固定“Execute one bounded native action”的简化记录。
- 根据 benchmark profile 提供历史/当前图片标签、必要相机与分辨率，不固定所有主图必须 512。
- 校验 provider 的图片数量上限、请求体和实际附件顺序，确保 RoboCasa 五张上限不会在后端被截成两张。
- 创建新的输入 profile/提示词快照和运行目录，更新冻结 lock；旧 campaign 不重写、不混分。留存旧输入结果用于对照。

### 7.2 SFT 采集与导出

- 不再 `frames[:image_limit]` 选图，读取相机 profile，特别补足 RoboCasa wrist、去掉 MetaWorld 重复视角，按 ManiSkill 任务确认手腕可用性。
- `_request_messages` 不再独立裁剪五轮多模态历史；使用四组文本历史＋profile 图片窗口。
- 每步调用共享字段白名单和回执构造器，增加实际控制步数、本体状态差分、图片身份和可用性信息。
- Qwen/DeepSeek 等 provider 的序列化差异只放在接口适配器里，不改变模型可见语义。
- 导出必须使用当时真实发送的输入包；图片顺序转为 Swift `images` 和占位符并逐一核验。
- 逐决策样本只监督本轮目标；历史 XML、user 状态、图片标签和宿主回执不进入目标 loss。现有 answer-only 策略若保留，明确记录它与 GRPO 生成思考监督的差异。
- 原来用不同相机/历史采集的数据，不得改写 prompt 后宣称老师是在新输入下作出的动作。它可以作为标注清晰的离线重构数据另行研究，不能混入“原始同输入采集”验收。
- 图片被删的审计记录不能导出为完整视觉 SFT 样本；仍保留动作/错误审计。

### 7.3 Swift GRPO

- `_image_base64` 的单相机输入与独立 prompt 替换为共享 profile 和上下文构造器。当前 PickCube 只需接入其实际可用的 ManiSkill profile，不因此扩展任务范围。
- 每轮实际采样前生成输入快照，替换无限累积图片和历史的行为；action/reward/MCP 调度与状态恢复逻辑不因输入格式调整而暗中改变。
- **每个生成回复的 logprob 必须在它实际生成时的上下文下计算。** 使用滑窗、重新打包图片、移除历史 thinking 后，不能简单把整个 episode 拼成一段普通对话重新编码计算 loss。
- 本机 Swift 4.4.2 需要验证按轮保存/编码 trajectory 条件上下文的方案，或实现等价的训练输入适配；仅保存 `response_token_ids` 本身不足以解决上下文不一致。
- 保存每轮原始生成 token IDs、对应 rollout logprobs、响应 mask、prompt tokens、图片顺序及 episode/turn 映射。保持每轮 reward/advantage 归属，不能因拆分编码把轨迹奖励错误重复累计。
- 历史 XML 作为当前轮条件不应重复计算当前轮生成 loss；它可以在其原本生成的那一轮接受监督。宿主回执/图片标签/预算始终屏蔽。
- 原始生成 thinking 是否监督按明确配置处理，不把序列化或裁剪后的文本配上裁剪前 logprobs。
- 没完成逐轮条件上下文与 loss 对齐验证前，不开启正式滑窗训练，也不能用训练保留全历史、评测只保留四轮的办法假装已统一。
- 保留已授权的模型初始化策略；本文不要求加载历史 LoRA、不要求额外短 SFT。新输入实验用独立运行身份，记录初始化来源。

## 8. 数据与可视化的审计字段

每次运行至少记录 `input_protocol`、`profile_id/hash`、输出协议、prompt 版本、模板/provider 适配版本、代码 revision、控制契约版本及模型生成配置。

每次模型请求至少记录：

- 规范输入包与最终 provider/Swift 渲染后的实际输入。
- 有序图像证据，源相机、时刻、hash、大小，以及去重/缺失/裁剪原因。
- 选中的历史决策 ID、上下文裁剪记录和 token 数。
- 原始模型回复、解析动作、执行请求和真实回执。
- 训练条件下的生成 token/logprob/mask 和原始 episode/turn 引用。

查看器应新增“本轮模型实际输入”视图：只显示该轮实际送入的图片、状态、反馈和历史索引，并与“宿主完整审计/评分”分开。当前查看器中保存的相机帧、reward 和对象位置不自动等于模型可见信息。

历史文件格式可以不同，读取器按 schema 适配；不得仅因页面统一展示就宣称旧数据输入已经一致。

## 9. 验收与实施顺序

1. **环境契约和 profile 预检**：四个 benchmark 核对真实控制模式、动作坐标/单位/夹爪方向、相机身份和可用性。缺失项作为显式预检问题，不靠模型猜。
2. **共享构造器离线验收**：输入同一份 observation/回执/历史，三个入口产出的规范包与图片索引一致；允许差异仅限列明的任务角色和模型模板。
3. **各 benchmark 小样本 canary**：观察、移动、夹爪、无效 XML、环境提前终止、图像缺失/重复、传输结果未知都覆盖。核实模型实际请求而非仅查看落盘帧。
4. **Swift 编码和 GRPO 条件一致性**：真实多轮滑窗下逐轮检查上下文、图片顺序、token IDs、logprob 长度及 loss mask；检查拆分轮次后的奖励归属。SFT 当前轮目标与历史屏蔽也需验收。
5. **固定任务/seed 的输入对照**：先比较“明确契约＋反馈＋图片标签”与旧输入，再比较 profile 的历史图/分辨率；避免同时换模型、预算和控制器。统计有效 XML、输出截断、重复观察、实际移动量、控制预算利用、任务成功和 token/延迟成本。
6. **正式发布**：冻结输入 profile 和快照，三个入口同时采用，启动独立结果目录。验收结论按 benchmark 列出，不以一个 PickCube canary 声称四环境都已通过。

语义对齐是硬验收，任务成功率提升是需要实验回答的问题。第一版相机/历史配置是明确的实施起点，不宣称已经性能最优。

## 10. 最终完成标准

**同一环境 profile 下，baseline、SFT、GRPO 看见相同类型的证据、同样的动作反馈、同样的有限历史，并按同一真实输入进行生成和训练。** 不同 benchmark 的相机数量与动作契约可以不同，但必须固定、可审计，不能由各链路自行猜测或静默降级。
